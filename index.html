Final year project · iOS app

Accessible Navigation

Walking directions that account for a wheelchair, walker or cane, with augmented-reality guidance and on-device hazard detection.

Most navigation apps assume everyone walks at the same pace over any surface. This app asks for the user's mobility aid, plans routes around steps and kerbs using OpenStreetMap data, and scales the journey time to that aid's pace. During navigation the camera shows arrows on the ground and flags potholes, slippery surfaces, broken tactile paving and obstructions.

What I built

  • Barrier-aware route planning from OpenStreetMap and OpenRouteService data, with four mobility profiles.
  • AR route guidance on ARKit (iOS) and ARCore Geospatial (Android), through a custom Swift native module.
  • On-device YOLO26n hazard detection, converted to Core ML and run at 10 Hz.
  • Text size, dark mode and spoken-turn settings, because the people using it may need them.

Soft skills in practice

  • Empathy. The app starts from the user's mobility aid, not from a generic walker. A wheelchair, walker and cane each change the route, the pace and the warnings, and the settings screen explains that in plain words.
  • Research. Journey times come from published walking-speed figures for each aid, instead of one pace for everyone.
  • Judgement under limits. I scoped it iOS-first and chose which features to finish properly, rather than spreading thin across both platforms.

React Native, Swift, ARKit, Core ML, YOLO26, OpenStreetMap

Web app · built end to end

Qtic event ticketing

Browse events, pick a session, pay and get a QR ticket. Organisers publish events and scan tickets at the door.

Qtic works for guests without an account, so buying a ticket takes one short form. Organisers apply to be approved by an admin, create events with multiple sessions and ticket types, and check people in by scanning their QR code.

What I built

  • Responsive React interface with guest checkout, a cart and QR-code tickets.
  • Serverless Firebase backend: Firestore, Auth and Cloud Functions.
  • Role-based security rules (guest, user, organiser, admin) with automated tests.
  • Billplz payments, transactional email and a GitHub Actions deploy pipeline.
  • Admin-approved organiser onboarding, with a dashboard for each role.

Soft skills in practice

  • Ownership. I took it from the first screen to deployment: interface, database rules, payments, email and the pipeline.
  • Attention to detail. Money and access are where mistakes cost the most, so the security rules for each role have automated tests.
  • Clear documentation. A local-testing guide lets someone else run the whole app on their machine without touching the live project.

React (Vite), Tailwind CSS, Firebase, Billplz, Google Maps

Web app · built for a real breeder

Pet Breeder Genealogy Tracker

A family tree for hamster breeders, with a blood check that warns before two closely related animals are paired.

Sweet Pawz needed lineage, fur genetics and sale status in one place instead of scattered notes and photos. Each animal is a card in a generation-by-generation tree, and selecting two animals shows how closely they are related before a pairing is made.

What I built

  • Interactive tree with generations, parent links, filters and search.
  • Blood check for pairing, based on shared ancestors.
  • Records for fur type, pattern, carrier genes and status (own, for sale, sold, adopted).
  • Installable progressive web app that works offline and syncs through Firebase.

Soft skills in practice

  • Listening. It was built for a working breeder, so the records, fields and wording follow how a breeder already describes their animals.
  • Prioritising. Lineage, the blood check and sale status are the core, with search and filters to find an animal quickly.
  • Explaining clearly. The blood check says in a sentence how two animals are related, so a non-technical user can act on it.

JavaScript, HTML, CSS, Bootstrap, Firebase

Personal project · iOS app

Nutrition Tracker

A food log with an AI assistant that can look up what you ate and suggest what fits the rest of your day.

Daily targets are shown as ranges rather than single numbers, and going over is a heads-up, not an error. The assistant can read the food log and ranges, and it always shows a draft and waits for confirmation before it changes anything.

What I built

  • Native SwiftUI app with SwiftData storage, kept on the device.
  • Assistant on the OpenAI Responses API with function calling and web search.
  • Barcode lookup through Open Food Facts and Malaysian food data from MyFCD.
  • Calendar and trend views, with nutrient colours chosen to stay distinguishable for colour-blind users.

Soft skills in practice

  • Honesty about limits. The assistant shows a draft and waits for confirmation before it changes anything, and the app does not claim to recognise food from photos.
  • Self-directed learning. A native iOS app with on-device storage and an AI assistant was new ground, so I worked from Apple's and OpenAI's documentation.
  • Care for users. Colours stay distinguishable for colour-blind users, and going over a target is shown as a heads-up, not an error.

Swift, SwiftUI, SwiftData, OpenAI API
